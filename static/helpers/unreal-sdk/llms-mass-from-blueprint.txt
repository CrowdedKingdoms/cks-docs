# Target an entity

This page has a C++ twin: [Target an entity, from C++](../from-cpp/target-an-entity.md).

On a Mass map you draw every other player as a crowd row, so there is no actor to drag a reference to. A **Crowdy Mass Entity Target** (the struct `FCrowdyMassEntityTarget`) names one of those players instead: which entity, and which world it lives in. You get one by tracing at the crowd, by overlapping it, or from an event, and every node on the pages after this one takes it. This page shows how to get a target and how to check it is still good.

## When you need a target

- To play an animation on a player you are looking at: [Send Crowdy Action](./call-an-event-on-it.md#send-a-one-shot-action-by-name).
- To send a Crowdy event to them: [Call Crowdy Event on Entity](./call-an-event-on-it.md#call-a-crowdy-event-on-an-entity).
- To read or write a field of their row: [Read and write its fields](./read-and-write-its-fields.md).
- To read a value the server keeps about them, such as a raider's health: [Read its server values](./read-its-server-values.md).

## The three ways to get one

A target has two read-only fields, so a graph cannot build one by hand. There are three ways to get one:

1. The **Target** pin inside **Out Hit** from a Crowdy Mass trace node.
2. The **Target** pin inside each element of **Out Overlaps** from a Crowdy Mass overlap node.
3. The **Target** output pin of a **Receive Crowdy Event on Entity** node, or of a **Receive Server Values Changed on Entity** node.

A target dies with the entity. If the player leaves and comes back, a target you stored before they left does not name the new entity. Check it with **Is Crowdy Mass Target Live** before you use it, as [below](#check-it-before-you-use-it).

## Trace for it

A Crowdy Mass trace works like the engine's trace nodes, and it also tests the crowd. It reports a hit on a crowd row and a hit on a near tier actor the same way. You do not branch on how the player is drawn. The nodes are in the category **Crowdy Mass|Trace**.

To let a player look at another and mark them:

1. In `BP_LanternPlayer`, add a variable named `TracedTarget` of type **Crowdy Mass Entity Target**. The Mass pages that follow read this variable.
2. In the event graph, add the **I** key event and drag off **Pressed**.
3. Add **Crowdy Mass Line Trace Single** and connect **Pressed** to it.
4. For **Start**, add **Get Player Camera Manager** (leave **Player Index** on 0), then drag off it and add **Get Camera Location**.
5. Drag off the same camera manager and add **Get Camera Rotation**, then drag off that and add **Get Forward Vector**.
6. Multiply the forward vector by 3000, add **Start** to the result, and connect the sum to **End**.
7. Set **Trace Channel** to **Visibility**, and leave **Trace Complex** off. Leave **Actors to Ignore** unwired. Set **Draw Debug Type** to **For Duration** while you test.
8. Drag off **Out Hit** and add the break node for the struct, so the fields show as pins.
9. Add a **Branch** after the trace and connect **Hit Mass Entity** to its **Condition**. This is the flag to branch on: it is true for a crowd row and for a near tier actor alike.
10. From **True**, add **Set TracedTarget** and connect the **Target** pin of the broken struct to it.

[Blueprint snippet: mass-trace-target, see /bp/unreal-sdk/mass-trace-target.txt]

Pan a Blueprint figure with the right mouse button. Press **Copy nodes**, then Ctrl+V in your own event graph.

### The shapes and modes

There are 24 trace nodes. A name is built from three choices, in this order:

**Crowdy Mass** + shape + **Trace** + **Single** or **Multi** + how the trace picks what it hits.

| How it picks | The end of the name | The pin that picks |
|---|---|---|
| By channel | nothing | **Trace Channel** |
| By object type | **For Objects** | **Object Types** |
| By collision profile | **By Profile** | **Profile Name** |

| Shape | Its own pins |
|---|---|
| **Line** | none beyond **Start** and **End** |
| **Sphere** | **Radius** |
| **Box** | **Half Size**, **Orientation** |
| **Capsule** | **Radius**, **Half Height** |

So **Crowdy Mass Sphere Trace Multi For Objects** and **Crowdy Mass Capsule Trace Single By Profile** are both real nodes, and **Crowdy Mass Line Trace Single** is the plain form. These are all 24, by their exact names in the palette:

| Node | By channel | For objects | By profile |
|---|---|---|---|
| Line, first hit | **Crowdy Mass Line Trace Single** | **Crowdy Mass Line Trace Single For Objects** | **Crowdy Mass Line Trace Single By Profile** |
| Line, every hit | **Crowdy Mass Line Trace Multi** | **Crowdy Mass Line Trace Multi For Objects** | **Crowdy Mass Line Trace Multi By Profile** |
| Sphere, first hit | **Crowdy Mass Sphere Trace Single** | **Crowdy Mass Sphere Trace Single For Objects** | **Crowdy Mass Sphere Trace Single By Profile** |
| Sphere, every hit | **Crowdy Mass Sphere Trace Multi** | **Crowdy Mass Sphere Trace Multi For Objects** | **Crowdy Mass Sphere Trace Multi By Profile** |
| Box, first hit | **Crowdy Mass Box Trace Single** | **Crowdy Mass Box Trace Single For Objects** | **Crowdy Mass Box Trace Single By Profile** |
| Box, every hit | **Crowdy Mass Box Trace Multi** | **Crowdy Mass Box Trace Multi For Objects** | **Crowdy Mass Box Trace Multi By Profile** |
| Capsule, first hit | **Crowdy Mass Capsule Trace Single** | **Crowdy Mass Capsule Trace Single For Objects** | **Crowdy Mass Capsule Trace Single By Profile** |
| Capsule, every hit | **Crowdy Mass Capsule Trace Multi** | **Crowdy Mass Capsule Trace Multi For Objects** | **Crowdy Mass Capsule Trace Multi By Profile** |

- **Single** returns the first blocking hit in **Out Hit**. **Multi** returns every hit along the trace in **Out Hits**, an array.
- Every trace node returns a bool.
- The pins after the shape pins are the same on every node: **Trace Complex**, **Actors to Ignore**, **Draw Debug Type**, then the output.
- Under **Advanced**: **Ignore Self** (on), **Trace Color**, **Trace Hit Color**, **Draw Time** (5 seconds), **Draw Mass Candidate Shapes** and **Draw Spatial Grid Cells**. The last two draw the crowd's broad-phase shapes and grid cells for debugging.

## Overlap for it

An overlap node finds the entities inside a volume. The nodes are in the category **Crowdy Mass|Overlap**, and each returns a bool and fills **Out Overlaps** with an array of `FCrowdyMassOverlapResult`. There are ten, listed here by their exact names:

| Shape | Actors | Components |
|---|---|---|
| Sphere | **Crowdy Mass Sphere Overlap Actors** | **Crowdy Mass Sphere Overlap Components** |
| Box | **Crowdy Mass Box Overlap Actors**, **Crowdy Mass Box Overlap Actors With Orientation** | **Crowdy Mass Box Overlap Components**, **Crowdy Mass Box Overlap Components With Orientation** |
| Capsule | **Crowdy Mass Capsule Overlap Actors**, **Crowdy Mass Capsule Overlap Actors With Orientation** | **Crowdy Mass Capsule Overlap Components**, **Crowdy Mass Capsule Overlap Components With Orientation** |

The shape pins are **Sphere Pos** and **Sphere Radius**, **Box Pos** and **Box Extent**, or **Capsule Pos**, **Radius** and **Half Height**. The **With Orientation** forms add **Orientation**. All of them take **Object Types**, **Actors to Ignore**, and either **Actor Class Filter** (the Actors forms) or **Component Class Filter** (the Components forms).

Loop over **Out Overlaps** with a **For Each Loop**. Branch on **Overlap Mass Entity**, then use **Target**. Each overlapping entity is reported once, whichever way it is drawn.

:::caution[A class filter applies to actors only, never to crowd entities.]
Every crowd entity inside the volume that passes **Object Types** is reported whatever **Actor Class Filter** or **Component Class Filter** says, including a close player whose near tier actor the filter rejected. Branch on **Overlap Mass Entity** rather than relying on the filter to exclude the crowd.
:::

## Read the hit

**Out Hit** is a `FCrowdyMassTraceHit`.

| Field | What it holds |
|---|---|
| **Blocking Hit** | The trace hit something that blocks. |
| **Hit Mass Entity** | The hit landed on a Crowdy Mass entity, drawn as a crowd row or as a near tier actor. Branch on this. |
| **Hit Crowdy Entity** | The hit landed on a Crowdy entity. |
| **Hit Result**, **Actor**, **Component** | The engine's hit result and the actor and component it hit. |
| **UUID** | Who was hit. It is read from the entity, never from the near tier actor drawing it. |
| **Entity** | The Mass entity handle. |
| **Target** | The same hit as a send target. It is set only when **Hit Mass Entity** is true. |
| **Bone Name** | The bone that was hit. |
| **Hit Zone Name** | The zone the bone belongs to in the active hit zone table, or the table's default zone. |
| **Damage Multiplier** | The hit zone's multiplier. For a flourish only; see below. |
| **Instance Index** | Which crowd row was hit, or -1 for a hit on a near tier actor. |

An `FCrowdyMassOverlapResult` has **Overlap Mass Entity**, **Overlap Crowdy Entity**, **Actor**, **Component**, **UUID**, **Entity**, **Target** and **Instance Index**, with the same meanings, except that **Instance Index** is always -1 on an overlap.

**Get Entity** (pure, in **Crowdy Mass|Trace**) takes a hit and returns the Crowdy Mass entity object for it, or nothing if the hit was not a Crowdy Mass entity. Getting **Target** does not create that object and **Get Entity** does, so do not call **Get Entity** on every hit, and do not keep what it returns across frames.

The entity object has two pure nodes in **Crowdy Mass**, **Get Entity UUID** and **Is Entity Valid**. **Is Entity Valid** is true while the entity the object stands for still exists, and false once it is gone or its world has gone away.

:::caution[Never work out damage from Damage Multiplier.]
The multiplier comes from a table on the machine that ran the trace. The server never reads it. Use it for a hit marker or a damage number that the server's own result will replace.
:::

## Check it before you use it

**Is Crowdy Mass Target Live** (pure, in **Crowdy Mass|Target**) takes a target and returns true while it still names a live entity that is ready to be read or written. It asks the entity manager, so it is stricter than checking that the struct is filled in. Run it on a stored target each time you use it, and do nothing when it is false.

## Hit zones

Assign a hit zone table once, and every Crowdy Mass trace fills **Hit Zone Name** and **Damage Multiplier** from it.

1. Create a **Crowdy Mass Hit Zone Table** data asset (`UCrowdyMassHitZoneTable`). Each row of **Entries** has a **Bone Name**, a **Zone Name** and a **Damage Multiplier**. **Default Zone Name** (`Default`) and **Default Damage Multiplier** (1.0) answer for a bone with no row.
2. At startup, call **Set Crowdy Mass Hit Zone Table** with the asset. Call it once for the world, not on every pawn's Begin Play. A table lasts for that world only.

**Set Crowdy Mass Entity Trace Collision Enabled** switches one entity in or out of traces at run time. It takes the **Entity** handle from a hit and a bool, and returns false for an entity that was never given a trace collision.

## Gotchas

- **Nothing is traceable without the trace collision trait.** An entity with no trace collision never blocks a trace and never passes a filter. A config the SDK derives for you has it. A config you author yourself must include the **Crowdy Mass Trace Collision** trait, or the whole crowd stays untraceable and looks like a trace that is aimed wrong. The log names the fix once.
- **A very long or malformed trace is slower, not wrong.** A trace whose sweep radius or end points are not finite or are out of range, or a straight trace longer than the grid's **Spatial Grid Max Ray Cells** (see [Turn Mass on for a map](../turn-mass-on-for-a-map.md)), is no longer answered partly from the grid. It tests every tracked entity, which costs more but finds far entities the grid used to miss.
- **Targets exist in a play session only.** The Mass subsystem is created in Play In Editor and in a game, not in the editor world, and only when the map profile selects the **Crowdy Mass Rendering Backend**. On an actor pool map the trace and target nodes find nothing.

# Call an event on it

This page has a C++ twin: [Call an event on it, from C++](../from-cpp/call-an-event-on-it.md).

Once you have a [target](./target-an-entity.md), two nodes act on the player it names. **Send Crowdy Action** plays a one-shot animation by name, with nothing declared. **Call Crowdy Event on Entity** sends any Crowdy event of your own, so your own code runs on the machines that receive it. Both work whether the player is drawn as a crowd row or as a near tier actor.

## Choose between the two nodes

| | Send Crowdy Action | Call Crowdy Event on Entity |
|---|---|---|
| Use it for | "Everyone sees this player cheer" | An event of your own that also runs your code |
| What you declare | Nothing | A Crowdy event on the entity's actor class |
| What you pass | An action name from the class's anim set | The event's own parameters |
| Who it reaches | Everyone drawing the entity as a row or a near tier actor | The recipients the event's own setting names |

## Send a one-shot action by name

**Send Crowdy Action** (category **Crowdy Mass|Anim**) takes a **Target** and an **Action Name** from the class's anim set, and everyone drawing that entity as a crowd row or as a near tier actor sees the action, including you. The pins, the reasons it returns false and the Oakford cheer are on [Play poses and one-shot actions](../play-poses-and-one-shot-actions.md).

## Call a Crowdy event on an entity

Use this for an event you declared on the entity's actor class, in Blueprint with **Crowdy Replicates** ticked on a custom event, or in C++ with `CROWDY_EVENT`. See [RPC Events in Blueprint](../../runtime/rpc-events-blueprint.md).

In the Oakford square, `ALanternPlayer` declares `WaveTorch` (`ActionId`, `Variant`, `PlayRate`), a `SpatialMulticast` event marked an action. `BP_LanternPlayer` keeps a `TracedTarget` from [Target an entity](./target-an-entity.md#trace-for-it). To make the traced player wave their torch:

1. Add the **V** key event. From **Pressed**, check `TracedTarget` with **Is Crowdy Mass Target Live** and a **Branch**, then on **True** add **Call Crowdy Event on Entity** (category **Crowdy Mass|Events**).
2. In the **Event** dropdown on the node, pick `WaveTorch`. The node is now titled **Call WaveTorch on Entity**, with the class name under it.
3. Wire `TracedTarget` into **Target**.
4. Set the pins the node grew, one per parameter of the event: **Action Id** to 1 (the first action of the anim set, `Wave`), **Variant** to 0 and **Play Rate** to 1.0.

[Blueprint snippet: mass-call-event, see /bp/unreal-sdk/mass-call-event.txt]

Pan a Blueprint figure with the right mouse button. Press **Copy nodes**, then Ctrl+V in your own event graph.

The **Event** dropdown lists:

- the Crowdy events of the entity classes your map profile's Crowdy Mass backend binds;
- the Crowdy events of loaded classes that carry a Crowdy Entity component;
- the SDK's own events, under **Any Crowd Entity**, which can be sent to an entity of any class.

The events are grouped by class, and the grouping shows whenever more than one group has events, which on this node includes **Any Crowd Entity**. Picking an event picks the class that declares it. Defaults on the pins come from the event's own defaults. A parameter that is an array, set or map must be wired, because it cannot hold a typed-in value.

The event goes out as if it had been called on that player's actor, so its recipient setting decides who runs it. A `SpatialMulticast` event reaches everyone near the entity. See [Recipients and Routing](../../runtime/recipients-and-routing.md). On a machine that draws the player as a crowd row or as a near tier actor, the event's body runs on the per-class stand-in, and a near tier actor only draws the entity and plays its actions; see [Run your code on a crowd row](../run-your-code-on-a-crowd-row.md).

:::caution[Nothing tells the graph whether the event arrived.]
The node has no output for the result. A target that cannot be resolved, a class mismatch and a refused call all fail quietly, with a line in the log. A client that cannot resolve the entity's class yet also fails this way: add the class to **Preloaded Entity Classes** under **Project Settings, Plugins, Crowdy SDK, Replication**, as [Entities and Spawning](../../runtime/entities-and-spawning.md#a-dynamic-entity-can-appear-with-no-spawn-event-at-all) describes. Check **Is Crowdy Mass Target Live** first.
:::

### When the node will not compile

The node reports an error, on the node, when:

- no event is picked in the **Event** dropdown;
- the class that declared the event, or the event itself, does not exist: pick it again;
- the picked function is not a Crowdy event you can send, for example a handler that takes a payload;
- **Target** is not wired;
- a container parameter is not wired.

If you reshape the event later, for example by adding a parameter, the call logs an error telling you to recompile the Blueprint that calls it. Recompile it.

## Gotchas

- **An empty dropdown can mean "not yet".** While the asset registry is still scanning, a class bound only by a map profile can be missing. Wait for the scan, or turn on `crowdy.mass.nodes.trace 1` to see where the entries came from.
- **The event must be on the entity's own class.** An event declared on a component cannot run on a crowd row; see [Run your code on a crowd row](../run-your-code-on-a-crowd-row.md).
- **Anyone can call it.** Any client can send an event at any entity. Treat what arrives as a request to draw something, and keep anything that must be true on the server.

# Receive its events

This page has a C++ twin: [Receive its events, from C++](../from-cpp/receive-its-events.md).

When a Crowdy event arrives for a player you draw as a crowd row or a near tier actor, the SDK already runs the event's own body for you on the per-class stand-in; see [Run your code on a crowd row](../run-your-code-on-a-crowd-row.md). **Receive Crowdy Event on Entity** lets a graph of your own take the event instead, with the event's parameters as pins and the entity as a **Crowdy Mass Entity Target**. It is the receiving half of [Call Crowdy Event on Entity](./call-an-event-on-it.md#call-a-crowdy-event-on-an-entity).

## When you need this

- To draw something from one place, for every player, when an event arrives: a counter, a toast, a flare on the row.
- To handle an event in a graph that is not on the entity's own class, such as a manager or the game state.

If the event's own body already does what you want, you do not need this node. Binding it changes what runs; see [what a bound graph replaces](#what-a-bound-graph-replaces).

## Bind a graph to an event

In the Oakford square, the market wants a lantern flare on the row of any player who waves. `ALanternPlayer` declares `WaveTorch`, and `ULanternCrowdSubsystem` registered a `TorchBrightness` field on the crowd row (see [Read and write its fields](./read-and-write-its-fields.md)).

1. Open an **event graph**. The node cannot go in a function or macro graph, and pasting it there is refused.
2. Add **Receive Crowdy Event on Entity** (category **Crowdy Mass|Events**).
3. In the **Event** dropdown on the node, pick `WaveTorch`. The node is now titled **Receive WaveTorch on Entity**, with the class name under it, and it grows an output pin for each parameter of the event.
4. Wire **Event BeginPlay** into **Bind**. Do this from one object per machine, such as the game state or a manager actor. Each bound object runs for every event, so binding from every pawn runs your graph once per pawn.
5. From **On Event**, add **Is Crowdy Mass Target Live** on the node's **Target**, then a **Branch**.
6. On **True**, add **Set Crowdy Mass Field (Float)**. Set **Target** to the node's **Target**, **Field Name** to `TorchBrightness` and **Value** to 1.0.

[Blueprint snippet: mass-receive-event, see /bp/unreal-sdk/mass-receive-event.txt]

Pan a Blueprint figure with the right mouse button. Press **Copy nodes**, then Ctrl+V in your own event graph.

The write sets a new target brightness, and the crowd eases the torch toward it. The next `TorchBrightness` that arrives from the player replaces that target, and the torch eases back to what the player is really showing. If nothing is wired to **Bind**, the compiler warns that the node is never reached and listens for nothing.

:::note[The row still waves.]
The graph above flares the torch, and the row still plays the wave, because `WaveTorch` is marked an action and a bound graph keeps that action. See [what a bound graph replaces](#what-a-bound-graph-replaces).
:::

**Unbind** is optional. The binding also ends when the object that bound it, or its world, goes away. Binding the same object twice is the same binding, not a second one.

## What the pins give you

| Pin | Direction | What it is |
|---|---|---|
| **Bind** | in, exec | Start listening for this event on crowd entities. |
| **Unbind** | in, exec | Stop listening. |
| **Then** | out, exec | Continues as soon as the bind or unbind is done, so several of these chain. |
| **On Event** | out, exec | Runs once for every arriving event, on the game thread. |
| **Event** | in, dropdown | The Crowdy event to listen for. It is picked on the node and cannot be wired. |
| **Target** | out | The entity the event arrived for. It is valid for this run only and does not survive that entity being respawned. |
| One pin per parameter | out | The event's parameters, matched by name and type. |

:::caution[Everything On Event carries came from the player being watched.]
The parameters were chosen by the client you are observing and can be anything at all. Use them to decide what is drawn, never what is true. Keep health, loot and the like in a Server Object (see [Keep a record per entity](../../exec/keep-a-record-per-entity.md)) and read it with [Get Server Value](./read-its-server-values.md).
:::

## What a bound graph replaces

Binding this node counts as registering a handler for the event. While a handler is registered for an event, a crowd row does not run the event's own body. The stand-in body is the fallback for an event nothing took.

The action is not replaced. If the event is marked an action, such as `WaveTorch`, the row still plays it, so you do not need to start the animation yourself. A handler registered in C++ is different: it replaces the action write too, and writes the action itself if it wants one; see [Receive its events, from C++](../from-cpp/receive-its-events.md#what-a-bound-function-replaces).

## Which events you can receive

The **Event** dropdown lists the Crowdy events of the entity classes your map profile's Crowdy Mass backend binds and of loaded classes that carry a Crowdy Entity component. It does not list the events the crowd applies itself, such as `PlayCrowdyAction`. Those run their own body on every machine and hand nothing to a graph, and picking one is a compile error.

An event that has a parameter named `CrowdyMassTarget`, `Then` or `OutputDelegate` cannot be received, because those names are used by the node's own pins. Rename the parameter.

## Gotchas

- **Inbound events are rate limited.** A target can receive 30 events a second, with a burst of 60. See [Run your code on a crowd row](../run-your-code-on-a-crowd-row.md) for what the limit is for.
- **Recompile after reshaping an event.** A bound graph is compiled against the event as it was. If you add or change a parameter, the bind is refused with an error that tells you to recompile the binding Blueprint.
- **The event still needs a recipient that reaches rows.** Only the two multicast recipients reach a machine that draws the player as a crowd row or a near tier actor. An `OwningClient` or `Host` event lands on one machine, which holds the player as a real actor. See [Recipients and Routing](../../runtime/recipients-and-routing.md).

# Read and write its fields

This page has a C++ twin: [Read and write its fields, from C++](../from-cpp/read-and-write-its-fields.md).

A crowd row keeps the values your game draws it with, such as the brightness of a torch, in fragments, which are small records of data that Mass owns. The field nodes read and write one of those values by name, for a **Crowdy Mass Entity Target**, with no C++ in the graph. A field is a visual: it holds what this machine draws, and it can differ from machine to machine.

:::note[Registering a field takes C++.]
The nodes work only on names your game registered in C++. The fragment, the trait and the registration are on [Add your own crowd data](../add-your-own-crowd-data.md). A Blueprint-only project can still read and write every field a programmer registered.
:::

## When you need this

- To show something on the screen about the player you are looking at, from a value the row already holds.
- To make a row do something visible from a graph, such as flaring its torch.

For a value that has to be true, such as health, use [Read its server values](./read-its-server-values.md).

## Before you start: the name must be registered

No field is registered for you. The nodes see only the names your game registered in C++, once, under the name of the `CrowdyState` property or view-state field that lands there. In the Oakford square, `ULanternCrowdSubsystem` registers `TorchBrightness`, a float that reads and writes the torch's target brightness: a read returns the target, and a write sets a new target the crowd eases toward. See [Add your own crowd data](../add-your-own-crowd-data.md) and [Read and write its fields, from C++](../from-cpp/read-and-write-its-fields.md).

An unregistered name fails every read and write. The log warns `Nothing is registered as '<name>'` at most once every five seconds for a name, so a typo is easy to miss. Call **Is Crowdy Mass Field Registered** (pure, category **Crowdy Mass|Fields**) with the name once at startup and log a warning if it is false.

## The nodes

All of them are in the category **Crowdy Mass|Fields**. Each takes a **Target** and a **Field Name**, and returns a bool.

| Node | The field's type |
|---|---|
| **Get Crowdy Mass Field (Byte)**, **Set Crowdy Mass Field (Byte)** | `uint8`, and an enum member that is one byte wide |
| **Get Crowdy Mass Field (Integer)**, **Set Crowdy Mass Field (Integer)** | `int32` exactly |
| **Get Crowdy Mass Field (Float)**, **Set Crowdy Mass Field (Float)** | `float` or `double` |
| **Get Crowdy Mass Field (Boolean)**, **Set Crowdy Mass Field (Boolean)** | `bool`, including a bitfield |
| **Get Crowdy Mass Field (Vector)**, **Set Crowdy Mass Field (Vector)** | `FVector` |
| **Is Crowdy Mass Field Registered** | pure; takes a name only |
| **Is Crowdy Mass Target Live** | pure; takes a target only |

The getters have an **Out Value** pin. The setters have a **Value** pin. Unlike a replicated state field, a field read by name accepts a bitfield `bool`.

## Read a field

1. Get a [target](./target-an-entity.md) and check it with **Is Crowdy Mass Target Live**.
2. Add **Get Crowdy Mass Field (Float)**. Set **Target**, and type `TorchBrightness` into **Field Name**.
3. Use **Out Value** only when the node returns true.

## Write a field

1. Add **Set Crowdy Mass Field (Float)** after the live check.
2. Set **Target**, type `TorchBrightness` into **Field Name**, and set **Value**.
3. The node returns true when the write happened.

## When a read answers false

The node returns false for any of these:

- The name is not registered. Check it with **Is Crowdy Mass Field Registered**.
- The entity is gone, or its target is stale.
- The entity has no fragment of the registered type. An entity built from a different config can lack a fragment another one has.
- The field is not of the type the node reads. Read an `int32` with the Integer node, not the Float node.
- Mass is processing right now. See the caution below.

## What a write means

:::caution[A write is a visual, and it is local.]
The same field on the same entity holds different values on two machines. Nothing mechanical may be decided from one. Registering a field also gives every graph write access to it, so register only fields that are yours and safe to draw from. Anything a peer must not be able to influence belongs in a Server Object; see [Keep a record per entity](../../exec/keep-a-record-per-entity.md).
:::

A write lasts only until the next value arrives. In the Oakford square, `TorchBrightness` lands on the torch's target brightness, so your write sets a new target, and the next `TorchBrightness` that arrives from the player replaces it.

:::caution[An access made while Mass is processing is refused.]
A graph reached from inside a Mass processing step would race the processors that read the same fragment. So would an ordinary tick that overlaps a Mass phase. The access is refused and logged: an error for a write, a warning for a read. The log line repeats at most once every five seconds for a field name. A refusal from an ordinary tick comes and goes, because Mass phases run alongside the game thread. Doing the work from a phase-end delegate, or from a broadcast deferred to the end of the frame, avoids it entirely; that is C++ work, described on [the C++ page](../from-cpp/read-and-write-its-fields.md#when-a-read-answers-false).
:::

## Set a pose by name

The pose of a row has its own node, because it is not a plain field. **Set Crowdy Mass Entity Pose** (category **Crowdy Mass|Anim**) takes a **Target** and a **Pose Name**, and puts the row in the pose of that name from its class's anim set.

- A **Pose Name** of `None` clears the pose.
- A name the anim set does not author also clears the pose, and says so in the log.
- It returns false, and does nothing, if the entity is gone, has no pose fragment, Mass is processing, or you named a pose for an entity whose class this client cannot resolve yet. Add the class to **Preloaded Entity Classes** under **Project Settings, Plugins, Crowdy SDK, Replication**; see [Entities and Spawning](../../runtime/entities-and-spawning.md#a-dynamic-entity-can-appear-with-no-spawn-event-at-all).
- The pose is a visual. An arriving pose replaces one you set.

See [Play poses and one-shot actions](../play-poses-and-one-shot-actions.md).

## Gotchas

- **A name is claimed across the process.** Two different fragment fields cannot share a name.
- **Reads are values, not references.** A node hands back a copy, never a pointer into the row, because Mass moves an entity's data when its archetype changes.

# Read its server values

This page has a C++ twin: [Read its server values, from C++](../from-cpp/read-its-server-values.md).

The values the server owns about a player or a creature, such as health, loot or a team's orders, are what is true. They cannot live on an actor for a crowd row, because a crowd row has no actor. They live in a Server Object that keeps **a record per entity**, and a row reads its own record in place. Nothing is copied into a fragment, and nothing runs per row per frame: the work is one pass over a batch of changed records.

The Server Object type and its server code are on [Keep a record per entity](../../exec/keep-a-record-per-entity.md), and this page does not repeat them. It covers what a crowd adds: the setup on the entity's class, and the nodes a row uses.

## When you need this

- To show a value on a player or creature you are looking at: a health bar over a raider.
- To react when a value changes: a bar that moves, a marker that appears.

The pose, the torch and the wave are view state. A modified client can lie about them, and the worst it can do is change what you see. A server value is the truth, and a player may only read what the server chose to send them.

## Set up the class

On the Oakford north road, the raiders are `BP_Raider`, keeping a record each in `CSO_Raider` (see [Raiders on the north road](../../exec/examples/raiders-on-the-north-road.md)). On a Mass map the players who watch the road draw each raider as a crowd row, and a row reads the same record.

1. **Make the type.** A Server Object definition with **Holds** set to **A Record per Entity**, whose server code adds a record for each entity, keyed by the entity's id. Each variable is **Server Only**, **Everyone**, **Owner Only** or **Team Only**. `CSO_Raider` has `Health` for **Everyone**, `Loot` for **Owner Only** and `Hideout` for **Team Only**.
2. **Put the component on the class.** The entity's actor class carries a **Crowdy Server Object** component whose **Definition** is that type. It can be native, in the Blueprint, or inherited. The SDK reads it once for the class, from the class default object. `BP_Raider` has one with **Definition** `CSO_Raider`. See [Add the component](../../exec/from-blueprint/get-a-server-object.md#add-the-component).
3. **Pick the object with the component's Instance Mode.** Rows follow only a mode that is the same for the whole class:

   | Instance Mode | What the rows read |
   |---|---|
   | **Only One Instance** (a setting of the type) | The type's one object. It wins over every Instance Mode. |
   | **Instance Id**, with an id typed | The object with that id. |
   | **This Actor's Area** | The objects of the areas around the local view. |

   With **Signed-In Player**, **This Actor**, **Player's Team** or **From Server Value**, the rows get no server values, and the log says why once for the class.
4. **Use the entity's id as the record id.** A row's record is the one whose id is the entity's UUID as 32 hex digits, the form a census of the world reports as `uuid`.

With **This Actor's Area**, the game follows the areas within the type's **Areas Followed Around a Player** of the local player's pawn or camera, and moves them as the view moves. A value of 1 means the 3 by 3 areas around the view. It lets go of an area only when the view is more than that radius plus one away, so a border does not flap. With no pawn or camera to follow, no area is followed and the rows read nothing.

## Read a value

**Get Server Value** is in the category **Crowdy Mass|Server Values**. Its pins are **Target**, **Name** and **Value**.

1. Get a [target](./target-an-entity.md) of a raider with a trace. You may check it with **Is Crowdy Mass Target Live** first; the graph below leaves that out to stay short.
2. Add the **H** key event, and from **Pressed** add **Get Server Value**. Wire `TracedTarget` into **Target**.
3. Type `Health` into **Name**. It is the variable's name in the asset.
4. Add an Integer variable named `Health` to the Blueprint, then drag it in and choose **Set Health**. Connect **Value** to it. The pin takes the type of whatever you connect.
5. Connect the node's return value to a **Branch**. Use **Value** only when the node returns true.
6. From **True**, add **Set Light Color** with the `Torch` light component of the player as its target. Connect a **Select Color** to **New Light Color**, with red in **A** and white in **B**.
7. Get `Health`, connect it to a `<=` node with 10 in its second input, and connect the result to the **Pick A** pin of **Select Color**. The torch turns red at 10 health or less, and white otherwise.

[Blueprint snippet: mass-server-health, see /bp/unreal-sdk/mass-server-health.txt]

Pan a Blueprint figure with the right mouse button. Press **Copy nodes**, then Ctrl+V in your own event graph.

The node returns true only for a value the server sent that fits the type of **Value**. The server never sends a value the player may not receive, such as an **Owner Only** value of an entity they do not own. The node returns false for it.

## React to a change

**Receive Server Values Changed on Entity** is the twin of [Receive Crowdy Event on Entity](./receive-its-events.md). It runs part of a graph whenever the server values of a row change.

1. Open an **event graph**. The node cannot go in a function or macro graph.
2. Add **Receive Server Values Changed on Entity** (category **Crowdy Mass|Server Values**).
3. Set **Entity Class** to `BP_Raider`. The node listens to rows of that class and its subclasses. The node is an error without a class, and a warning if the class has no Crowdy Server Object component that reads a record per entity.
4. Wire **Event BeginPlay** into **Bind**. If nothing runs into **Bind** the compiler warns that the node is never reached.
5. From **On Changed**, use **Target** and **Changed**. Call **Get Server Value** on **Target** for each variable you care about.

| Pin | Direction | What it is |
|---|---|---|
| **Bind** | in, exec | Start listening. |
| **Unbind** | in, exec | Stop listening. The binding also ends when the object or its world goes away. |
| **Entity Class** | in | The actor class whose crowd rows are listened to, with its subclasses. |
| **Then** | out, exec | Continues as soon as the bind or unbind is done. |
| **On Changed** | out, exec | Runs for each change of a row of that class. |
| **Target** | out | The row. |
| **Changed** | out | An array of strings: the variables that changed, as **Get Server Value** takes them. Empty when the entity's record was removed. |

A record can arrive before its row exists. The record is kept, and the event runs once, with the current values, when the row appears. A row that moves from one followed area into the next does not see its record removed and added again.

## A near tier actor

A class that promotes to the near tier (see [Promote close entities to actors](../promote-close-entities-to-actors.md)) reads and hears the same values through its **Crowdy Mass Near Tier** component, `UCrowdyMassNearTierComponent`. Both answer for the entity the near tier actor stands in for, so the actor and its row never disagree.

- **Get Server Value** on the component has the pins **Name** and **Value**. It reads the bound entity's variable.
- **On Server Values Changed** is an event on the component with a **Changed** array. In `BP_LanternPlayer_Shell`, select the **Crowdy Mass Near Tier** component and click the plus beside the event in the Details panel.

## Gotchas

- **Read to draw.** The values are the server's. Change them by calling a Server Function, not from here.
- **Owner Only and Team Only values arrive later** than **Everyone** values, because they are fetched, at most once a second for each followed area.
- **The first values are not instant.** A row drawn the moment a player enters an area reads nothing until the object has been read.
- **A class stays followed for the life of the world** once a row of it has been seen.
- **A row gets no values.** Work through the checklist on [Fix a crowd that does not look right](../troubleshooting.md).
