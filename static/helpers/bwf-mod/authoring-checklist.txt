BWF PLAYER-MOD AUTHORING CHECKLIST

INPUTS
- appId: BWF app id
- gridId: a grid currently owned by the author
- name: lowercase crate-style module name, unique in the grid
  (a server mod's name is 1-48 lowercase letters, digits, - or _)
- target: SERVER (a ck-exec mod) or CLIENT (a browser module)

REQUIRED SOURCE MAP (each target is one crate)
{
  "Cargo.toml": "<contents of Cargo.toml>",
  "src/lib.rs": "<contents of src/lib.rs>"
}

SERVER TARGET: A CK-EXEC MOD
1. Start from the mod starter: execModStarter(appId).
2. Build the crate with execModBuild(appId, crate: { name, files }), then poll
   execModBuildStatus until status is succeeded.
3. Deploy it to the grid with execModDeploy(appId, gridId, name, buildId).
4. Switch it on with execModSetEnabled(appId, gridId, name, enabled: true).
5. Players in the grid call it as node type mod:<name>, keyed by the grid id.
6. Read its log lines with execModLogs.

CLIENT TARGET: A BROWSER MODULE
1. Deploy CLIENT source with playerComputeDeploy.
2. Poll playerComputeVersions until compileStatus is succeeded.
3. Visitors query gridClientMods, display authorCapabilitySummaryJson, and
   call trustGridAuthor with the exact authorCapabilityHash.
4. Fetch client bytes with playerCodeClientArtifact(attachmentId: ...).
5. Poll only gridClientMods metadata; stop on removal/hash change/grid exit.

INVARIANTS
- SERVER: Rust + ckx-sdk; dependencies are ckx-sdk, serde and serde_json only.
- SERVER: runs as the current grid owner, in the owner's own sandbox, and can
  read and change only its own grid.
- CLIENT: Rust + crowdy-compute-sdk = "0.1.5"; dependencies must be allow-listed.
- CLIENT: runs in the browser worker with no DOM/token/network access.
- hud_set and overlay_draw are host-rendered presentation requests.
- Local parser/index diagnostics are advisory; the platform build is authoritative.
- Local tooling does not provide borrow checking, full trait/proc-macro
  resolution, Cargo build-script execution, or full build semantics.
- There is no authoring endpoint/token or server language-service fallback.
- Trust is scoped to visitor + app + grid + author + aggregate capability hash.
- Any capability widening requires a new explicit trust action.
